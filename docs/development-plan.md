# 開発計画

## 目的

このリポジトリは、Waveshare `RP2040-Keyboard-3-PLUS` を題材に、Zig でキーボードファームウェアを書くことを学ぶための学習プロジェクトです。

最初から完成度の高いキーボードファームウェアを作ることが目的ではありません。組み込みキーボードファームウェアを構成する各レイヤーを、段階的に理解することを重視します。

学習対象は主に以下です。

- RP2040 向けファームウェアのビルド設定
- GPIO 入出力
- キースキャン
- チャタリング対策
- USB HID キーボードレポート
- 将来的な RGB LED 制御
- 将来的なキーマップ / レイヤー / マクロ機能

プロジェクトは、小さく検証可能なステップで進めます。

## 対象ハードウェア

対象ボード:

- Waveshare RP2040-Keyboard-3 / RP2040-Keyboard-3-PLUS
- RP2040 ベースの 3 キー USB キーボード

既知、または現時点で想定している GPIO マッピング:

| 機能 | GPIO |
|---|---:|
| Key 1 | GP12 |
| Key 2 | GP13 |
| Key 3 | GP14 |
| オンボード LED またはデバッグ用 LED | GP25 |
| RGB LED / WS2812B データ線 | GP18 |

キー入力は active-low と想定します。

- 離している: HIGH
- 押している: LOW

これらの前提は、公式回路図および実機の挙動で確認します。

## 基本方針

### レイヤーごとに学ぶ

いきなり USB HID や本格的なキーボードファームウェア設計には進みません。

以下の順番で進めます。

1. ファームウェアをビルドできるようにする
2. LED を点滅させる
3. 1つのキーを読む
4. 3つのキーを読む
5. チャタリング対策を入れる
6. USB HID キーボードレポートを送る
7. キーマップの抽象化を入れる
8. RGB LED 制御を試す
9. レイヤー / マクロ / カスタム動作を試す

### コードはシンプルに保つ

このプロジェクトは学習目的です。

早い段階で QMK のような大きなアーキテクチャを作ろうとせず、明示的で読みやすいコードを優先します。

### 各ステップを実機で確認する

各マイルストーンでは、実際にボードへ書き込めるファームウェアイメージを作り、手元のハードウェアで挙動を確認します。

### USB HID は後のマイルストーンにする

GPIO 入出力とキー状態管理を理解してから USB HID に進みます。

### 破壊的操作を避ける

コーディングエージェントは以下を行ってはいけません。

- 明示的な指示なしに commit する
- 明示的な指示なしに push する
- 破壊的な git コマンドを実行する
- 方針説明なしにリポジトリを大きく書き換える
- 理由なく依存関係を大幅に更新する

## 現在のフェーズ

現在は初期 bring-up フェーズです。

直近の目標は以下です。

> MicroZig ベースの RP2040 ファームウェアをビルドし、`.uf2` ファイルを生成できるようにする。そのうえで、GP12 / GP13 / GP14 のキー入力に応じて GP25 を制御できるようにする。

最初のマイルストーンでは、USB HID は意図的に対象外とします。

## マイルストーン

### Milestone 1: ビルド設定

目的:

- MicroZig ベースの RP2040 ファームウェアプロジェクトを構成する
- `zig build` で `.uf2` ファイルを生成する

タスク:

- Zig のバージョンを確認する
- MicroZig の依存関係設定を確認する
- `build.zig` を RP2040 向けに設定する
- 初期 target として Raspberry Pi Pico 互換の RP2040 target を使う
- ファームウェア名を安定させる
  - 例: `zig-keyboard-lab`
- `zig build` でファームウェア成果物が生成されることを確認する

期待する出力:

```text
zig-out/firmware/zig-keyboard-lab.uf2
zig-out/firmware/zig-keyboard-lab.elf
```

完了条件:

- `zig build` が成功する
- `.uf2` が生成される
- ビルド手順がドキュメント化されている

### Milestone 2: LED Blinky

目的:

- 自作ファームウェアがボード上で動作することを確認する

タスク:

- GP25 を output に設定する
- GP25 を 500ms 程度の間隔でトグルする
- ファームウェアをビルドする
- 生成された `.uf2` を手動で書き込む
- 実機上で LED の挙動を確認する

完了条件:

- ボード上で自作ファームウェアが動作する
- GP25 の状態変化が視認できる、または同等の観測可能な挙動が確認できる

補足:

- このボードで GP25 が視認可能な LED に接続されていない場合は、GP25 が利用可能か、別のデバッグ出力が必要かを確認する

### Milestone 3: 1キー入力

目的:

- 1つの物理キーを読む

タスク:

- GP12 を pull-up 付き input に設定する
- LOW を押下状態として扱う
- GP12 が押されたら GP25 を点灯する
- GP12 が離されたら GP25 を消灯する

完了条件:

- Key 1 を押すと LED の状態が変化する
- 押下状態と解放状態を確認できる

### Milestone 4: 3キー入力

目的:

- 3つの物理キーを読む

タスク:

- GP12 / GP13 / GP14 を pull-up 付き input に設定する
- 各キーを active-low として読む
- いずれかのキーが押されていたら GP25 を点灯する
- 必要に応じて、各キーの内部状態を単純な形で持つ

完了条件:

- 3つの物理キーをそれぞれ独立して検出できる
- どのキーを押してもデバッグ LED の状態が変化する

### Milestone 5: チャタリング対策

目的:

- 安定したキー状態を得るために、簡単な debounce 処理を追加する

タスク:

- 生のキー状態を保持する
- 安定したキー状態を保持する
- 前回の生状態を保持する
- 状態が変化してから 20〜30ms 程度同じ状態が続いた場合に、安定状態として受け入れる
- 実装は明示的で確認しやすい形にする

完了条件:

- 機械的なチャタリングによる誤検出が減る
- HID 実装に進める程度に、押下 / 解放の遷移が安定している

想定するデータ構造例:

```zig
const KeyState = struct {
    raw_pressed: bool,
    stable_pressed: bool,
    last_raw_pressed: bool,
    last_changed_ms: u64,
};
```

### Milestone 6: キーイベント検出

目的:

- 現在状態だけでなく、状態遷移を検出する

タスク:

- 押下イベントを検出する
- 解放イベントを検出する
- 現在押されている状態も取得できるようにする
- デバッグ出力手段があれば内部状態を出す
- デバッグ出力が難しい場合は LED パターンなどで観測する

完了条件:

- 以下を区別できる

  - キーが押され続けている
  - キーが今押された
  - キーが今離された

このマイルストーンは USB HID レポート送信の準備になります。

### Milestone 7: USB HID キーボード出力

目的:

- ボードを USB キーボードとして動作させる

タスク:

- Zig / MicroZig から TinyUSB を統合する最適な方法を調査する
- 最小の HID キーボードサンプルから始める
- 単純なキーボードレポートを送信する
- 3つのキーを単純な入力にマップする

  - 例:

    - Key 1: Ctrl
    - Key 2: C
    - Key 3: V

完了条件:

- ホスト PC がボードを USB HID キーボードとして認識する
- キーを押すと期待したキーイベントが送信される
- キーを離すと適切な release report が送信される

重要:

- GPIO 入力とチャタリング対策が動いてから、このマイルストーンに進む

### Milestone 8: キーマップ抽象化

目的:

- 物理キーと論理アクションを分離する

タスク:

- 物理キー識別子を定義する
- 論理アクションを定義する
- 単純なキーマップテーブルを追加する
- 設計は小さく読みやすく保つ

想定する形:

```zig
const PhysicalKey = enum {
    key1,
    key2,
    key3,
};

const Action = union(enum) {
    keycode: u8,
    modifier: u8,
    noop,
};
```

完了条件:

- スキャン処理を書き換えずにキーの動作を変更できる
- まだ単純な単一レイヤーのキーマップに留める

### Milestone 9: RGB LED 実験

目的:

- RGB LED を制御する

タスク:

- GP18 と WS2812B の前提を確認する
- MicroZig に PIO / WS2812 の参考実装があるか調べる
- まずは単色表示から始める
- その後、キー押下状態を色で表現する

完了条件:

- 自作ファームウェアから RGB LED を制御できる
- キー押下状態を視覚的に反映できる

### Milestone 10: レイヤーとマクロ

目的:

- キーボードらしいカスタム動作を試す

タスク:

- 単純なレイヤー概念を追加する
- 必要であれば hold/tap や modifier 動作を追加する
- マクロアクションは基本設計が安定してから追加する

完了条件:

- 3つの固定キーコード以上の動作を表現できる
- 実装が理解しやすい状態を保っている

## 推奨ワークフロー

各マイルストーンでは以下の手順で進めます。

1. 小さな Issue を作成、または更新する
2. 最小限のコード変更を行う
3. `zig build` を実行する
4. 必要に応じて手動で書き込む
5. 実機で起きたことを記録する
6. 得られた知見を docs に追記する

推奨するドキュメント:

```text
docs/development-plan.md
docs/hardware-notes.md
docs/build-and-flash.md
docs/experiments.md
```

## エージェント作業ルール

Codex CLI などのコーディングエージェントを使う場合は、以下を守ります。

- 最初に `AGENTS.md` を読む
- 変更前にこの開発計画を読む
- 現在のマイルストーンを明示する
- 編集前に変更意図を説明する
- 変更は小さく保つ
- ビルド設定やファームウェアを変更したら `zig build` を実行する
- 明示的な指示なしに commit / push しない
- ユーザーが求めていない限り、USB HID に先走らない

## 未解決の確認事項

- GP25 はこのボード上で視認可能な LED に接続されているか
- GP18 は本当に WS2812B のデータ線か
- PLUS 版と非 PLUS 版に電気的な差異はあるか
- Zig / MicroZig のバージョンをどれに固定すべきか
- Zig から TinyUSB を統合する最も素直な方法は何か
- 将来的に Raspberry Pi Pico target ではなく、このボード専用 target を定義すべきか

- VIA / Vial 対応
- Bluetooth 対応
- 省電力最適化
- 複数ボード対応
- 本番品質のファームウェア配布パッケージ
